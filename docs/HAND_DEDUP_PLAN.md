# 手の重複検出問題：原因と対策計画

## 起こった現象

`/home/gayagaya/video/new/GX010086.MP4`（人物 1 人、両手 = 本来 2 手）の v2 出力 JSON を見ると、
1 フレームあたりの手の数が **常に過剰**：

| 手数 | フレーム数 | 割合 |
|---|---|---|
| 1 | 18 | 1.1% |
| **2 (正解)** | **247** | **15.2%** |
| 3 | 808 | 49.6% |
| 4 | 403 | 24.7% |
| 5 | 104 | 6.4% |
| 6 | 50 | 3.1% |

正解（2 手）はわずか 15%。8 割以上のフレームで余計な手が混ざっている。

`handsonly.mp4` の左上に小さな浮遊メッシュが見えていたのもこの一部
（モニターに映った腕の反射が拾われている）。

### 個別フレームでの例（frame 100、5 手検出）

| hand | is_right | bbox (x1,y1,x2,y2) | 推定原因 |
|---|---|---|---|
| 0 | 0 (左) | 830, 902, 1185, 1201 | 左手 |
| 1 | 1 (右) | 816, 917, 1185, 1201 | ← **0 と同位置の二重検出** |
| 2 | 0 (左) | 1887, 883, 2211, 1129 | ← 3 と同位置の二重検出 |
| 3 | 1 (右) | 1865, 872, 2223, 1117 | 右手 |
| 4 | 0 (左) | 246, 0, 284, 43 | ← モニター反射（小サイズ、上端） |

## 根本原因

`demo_video.py::detect_hand_bboxes` のループ：

```python
left_hand_keyp  = vitposes['keypoints'][-42:-21]
right_hand_keyp = vitposes['keypoints'][-21:]
for keyp, side in [(left_hand_keyp, 0), (right_hand_keyp, 1)]:
    valid = keyp[:, 2] > 0.5
    if valid.sum() > 3:
        bbox = [...]; bboxes.append(bbox); is_right.append(side)
```

- ViTPose は **1 人物について 21 個の左手 keypoint + 21 個の右手 keypoint を必ず両方推定**する
- 人物検出 (body detector) で見つかった ROI ごとに、左用・右用の両方を bbox 化して HaMeR に流している
- 実際には 1 つの手しか写っていなくても、**L キーポイントも R キーポイントも信頼度 > 0.5** になることが多い → 重複
- さらに ROI が誤検出（鏡像・反射・人物の見間違い）なら、その分だけ余計な bbox が増える

検出 → HaMeR の流れが「**人物候補ごとに L/R 2 個ずつ盲目的に bbox を作る**」設計なので、重複は当然の帰結。

## 対策候補（独立に評価可能）

### A. L/R 排他選択
ViTPose の L 21pts / R 21pts のうち、**平均 confidence が高い方だけ採用**。

| メリット | 同一 ROI から最大 1 bbox に絞れる。実装数行 |
|---|---|
| デメリット | 「両手が画面に写っているのに ROI が両手をまたぐ」状況だと片方が落ちる |
| 期待効果 | hand0/1, hand2/3 のような **完全な L/R 二重検出を解消**。残るのは反射 hand4 のみ |
| 実装場所 | `detect_hand_bboxes` のループを書き換え |

### B. bbox NMS（IoU ベース）
出力 bbox 集合に対して **IoU > 0.6 なら低 confidence 側を捨てる**。

| メリット | A より一般的（L/R 関係なく重複を除去できる）|
|---|---|
| デメリット | confidence をきちんと保持してパスする必要あり |
| 期待効果 | A と同等 + 同じ手を別 ROI 経由で2回拾ったケースも除去 |
| 実装場所 | `detect_hand_bboxes` の return 直前 |

### C. 最小サイズフィルタ
bbox の **面積（または短辺）が閾値未満なら捨てる**。

| メリット | モニター反射のような小さい false positive を弾ける |
|---|---|
| デメリット | 画面の隅で本物の手が小さく写ったケースも落ちる |
| 期待効果 | 反射系の **hand4 を消す**。短辺 < 64 px くらいが目安（GX010086 hand4 は短辺 38 px）|
| 実装場所 | `detect_hand_bboxes` の bbox 計算後 |

### D. ViTPose confidence 閾値の引き上げ
現在 0.5 → 例えば 0.7 に。

| メリット | 弱い検出が全部消える |
|---|---|
| デメリット | 速い動きや陰の手が消える可能性 |
| 期待効果 | フレームあたり手数が全体的に減るが、副作用も大きい |
| 実装場所 | `detect_hand_bboxes` の `valid = keyp[:, 2] > 0.5` |

### E. 時系列 dedupe（temporal consistency）
フレーム間で bbox/wrist 位置の連続性を見て、突然出てくる単発検出を弾く。

| メリット | 反射のような **散発的な偽検出** を除去できる |
|---|---|
| デメリット | 後処理が重い、JSON 書き出し後に別パスが要る |
| 期待効果 | 反射の安定的除去、L/R flip の安定化（既に NEXT.md 「次の候補」にも挙がっている）|
| 実装場所 | JSON 書き出し後の post-process スクリプト |

## 推奨組み合わせ

> **A + C を同時投入**、その後で **B を追加**するか判断。

理由：
- **A（L/R 排他）**で同 ROI の二重検出を一発で消せる（最大の寄与）
- **C（最小サイズ）**で反射系を消せる、設定が簡単
- 残った重複（別 ROI 経由の同一手など稀ケース）に **B（NMS）**を追加
- **D（閾値上げ）は最後の手段**（副作用大）
- **E（時系列）は重い**ので、A/B/C で十分削れなければ後追い

## 期待効果見積もり（GX010086 ベース）

| 状態 | 手数=2 の割合 | 推定平均手数 |
|---|---|---|
| 現状 | 15% | 3.3 |
| A 投入後 | **~75%** | ~2.1 |
| A + C 投入後 | **~85%** | ~2.0 |
| A + C + B | **~90%** | ~2.0 |

数字は frame 100 のパターンを全フレームに敷衍した素朴推定。実測で要検証。

## 実装ステップ案

1. `detect_hand_bboxes` を `confidences` も一緒に返すように拡張（無侵襲）
2. **A: L/R 排他**を実装。`for keyp, side in [(L,0),(R,1)]:` をやめて `mean_conf` で勝敗を決める
3. 短いテスト動画（GX010086 から 30f 切る）で frame 100 が **2 手**に減ることを確認
4. **C: 最小サイズ**フィルタを追加（短辺 64px 閾値、調整可能オプション）
5. GX010086 全体で再走（GPU 1 単体で 20〜30 分見込み、新コードは inference が変わらないので速度は同等）
6. JSON で手数分布を再集計し、85% 目標を達成しているか確認
7. 不足なら **B（NMS）**を追加

## 副作用 / 注意

- **後方互換**: JSON の schema は変わらない（手数だけ減る）。下流が「2 手前提」で書かれていれば寧ろ正しくなる
- **wrist JSON 既存ファイル**: 既存 32+2 ファイルは現コードの結果。フィルタ投入後に再走すれば差し替え可
- **detect 順序**: 現在 bbox 配列の順序で `bbox_idx` を進めているので、削除は配列単位で揃えること（is_right 配列も同期）
- **`Hamer` クラス API には影響なし**（内部実装のみ）
